## 2. Platform Architecture

### 2.1 Umbrella Design and OTP Supervision

Prismatic Platform is structured as an Elixir umbrella project containing 141 OTP applications. Each application owns its supervision tree, configuration, dependencies, and test suite. The umbrella architecture provides strong boundary enforcement between subsystems while enabling shared compilation, coordinated releases, and cross-application protocol contracts.

The supervision hierarchy follows a defense-in-depth model. Top-level supervisors manage critical infrastructure services -- database connections, cache layers, telemetry pipelines, and the agent runtime. Mid-level supervisors isolate domain-specific subsystems such as OSINT collection, perimeter scanning, and due diligence workflows. Leaf-level supervisors manage individual workers, ensuring that a failure in any single intelligence task cannot cascade to affect unrelated operations.

Key applications in the umbrella include:

- **prismatic** -- Core coordination, health monitoring, and cross-application orchestration
- **prismatic_web** -- Phoenix LiveView dashboards serving real-time intelligence visualizations on port 4000
- **prismatic_api** -- Auto-introspecting REST gateway with OpenAPI 3.0 specification generation on port 4004
- **prismatic_agents** -- Runtime for 532 autonomous AIAD agents
- **prismatic_perimeter** and **prismatic_perimeter_web** -- External attack surface management with security ratings
- **prismatic_dd** -- Entity-centric due diligence platform
- **ai_drift** and **ai_drift_web** -- AI decision monitoring and drift detection
- **prismatic_osint_core** and **prismatic_osint_sources** -- OSINT collection framework with 121+ source adapters
- **prismatic_storage_core**, **prismatic_storage_ecto**, **prismatic_storage_ets**, **prismatic_storage_meilisearch**, **prismatic_storage_kuzudb** -- Polyglot storage layer with contract-tested adapters
- **prismatic_claude** -- LLM integration with session lifecycle, stack-based conversation tracking, and quality DNA persistence
- **prismatic_lean4** -- Formal verification bridge to the Lean 4 theorem prover
- **prismatic_deduction** -- Automated deductive reasoning with proof generation
- **prismatic_nabla** -- NABLA Infinity epistemic framework implementation

### 2.2 The Three Nested Levels (3NL) Framework

The 3NL architectural framework structures every subsystem into three composable layers:

**Level 1 -- Data Substrate.** All persistent state is managed through a polyglot storage layer. PostgreSQL serves as the primary relational store for structured entity data, audit logs, and transactional records. ETS (Erlang Term Storage) provides microsecond-latency in-memory caching for hot paths. Meilisearch powers full-text search and faceted filtering across intelligence records. KuzuDB handles graph-structured data for entity relationship mapping -- ownership chains, corporate hierarchies, and network topologies. Redis provides distributed caching and pub/sub messaging for cross-node coordination.

**Level 2 -- Logic and Reasoning.** Business logic is expressed as pure functions where possible, with side effects confined to system boundaries. Agent coordination follows the AIAD (Autonomous Intelligence Agent Definition) standard, which specifies a declarative format for agent capabilities, permissions, and interaction protocols. Epistemic reasoning is handled by the NABLA Infinity framework, which maintains belief graphs with provenance tracking, confidence scoring, and formal verification through the Trinity Gate.

**Level 3 -- Presentation and Interface.** Phoenix LiveView provides real-time server-rendered dashboards that update via WebSocket without requiring client-side JavaScript frameworks. The auto-introspecting REST API discovers all public functions across Prismatic facade modules at boot time, generates OpenAPI 3.0 specifications automatically, and exposes them through a generic dispatch controller. TailwindCSS with Flowbite components ensures consistent, accessible UI across all dashboard surfaces.

### 2.3 Event-Sourced Determinism

Every significant platform action is recorded as an immutable event. State is derived by replaying event sequences, making the entire system reproducible and auditable. This architecture provides several critical properties: temporal queries (the ability to reconstruct the exact state of any intelligence assessment at any past point in time), causal tracing (the ability to trace any conclusion back through the chain of evidence and reasoning steps that produced it), and regression safety (the ability to detect when a code change causes a previously correct conclusion to change).

## 6. Epistemic Framework: NABLA Infinity

### 6.1 Core Axioms

The NABLA Infinity framework governs all epistemic reasoning within the platform. It enforces seven non-negotiable axioms:

1. **Signal Plurality** -- No belief may be held based on a single signal. A minimum of two independent signals is required before any claim enters the belief graph. This prevents single-source dependency and reduces vulnerability to poisoned data.

2. **Contradiction Evidence** -- When contradictory signals are received, both sides must be preserved. The framework never silently discards contradicting evidence. Instead, it records the contradiction explicitly and adjusts confidence scores to reflect the epistemic tension.

3. **Absence Informative** -- The absence of expected signals is itself treated as evidence. When a source that should contain information about an entity returns empty results, this negative signal is recorded and factors into confidence calculations.

4. **Time Decay** -- All evidence carries mandatory timestamps, and confidence decays as evidence ages. The decay rate is configurable per domain -- threat intelligence decays faster than corporate registry data.

5. **Unknown Valid** -- "I don't know" is a legitimate and valued epistemic state. The system never fabricates certainty where none exists. Agents are required to propagate uncertainty rather than collapse it prematurely.

6. **Source Independence** -- Signals from independent sources receive higher combined weight than signals from correlated sources. The framework tracks source dependency graphs to prevent circular amplification of confidence.

7. **Provenance Mandatory** -- Every belief in the system is traceable to its originating evidence. No claim exists without an auditable chain of reasoning connecting it to raw observations.

### 6.2 The Trinity Gate

Before any high-confidence claim is accepted into the platform's belief graph, it must pass the Trinity Gate -- a four-layer verification mechanism:

1. **Structural Consistency** -- Graph-theoretic analysis ensures the claim does not create logical cycles, orphaned nodes, or structural contradictions in the belief graph
2. **Logical Consistency** -- Rule-based inference checks verify the claim against known logical constraints and domain-specific rules
3. **Formal Necessity** -- Modal logic analysis combined with Lean 4 theorem prover verification ensures the claim is formally sound
4. **Meta-Consistency** -- A final meta-level check verifies that the claim's acceptance would not degrade the overall coherence of the belief system

Confidence thresholds are context-dependent: critical decisions require 0.95 or higher, standard operations require 0.80, exploratory analysis accepts 0.60, and research queries accept 0.50.

## 7. Security Architecture

### 7.1 Color-Team Operations

The platform's security posture is maintained by 20 specialized agents organized into six color-coded teams:

**Gray Team (3 agents)** -- Boundary Exploration. Read-only exploration of specification gaps, edge cases, and affordance drift. The Gray team surfaces ambiguity without resolving it, feeding boundary discoveries to Red and Blue teams for adversarial testing and defensive hardening.

**Red Team (4 agents)** -- Adversarial Simulation. Simulates epistemic attacks using five attack primitives: truth distortion, confidence manipulation, signal poisoning, drift induction, and salience hijacking. All Red team operations execute exclusively in sandboxed environments with synthetic data.

**Blue Team (4 agents)** -- Epistemic Defense. Produces structured defensive evidence through authentication boundary monitoring, behavioral drift detection, and cross-domain signal correlation. Blue team output is grounded in NABLA axioms.

**Purple Team (4 agents)** -- Synthesis and Closure. The central hub for Red-Blue loop closure, holding sole authority for closure state transitions. Purple team detects false closure states and manages regression traps. Its operational principle: "Purple is the property of the system when it stops lying to itself."

**White Team (3 agents)** -- Constructive Verification. Proves system properties through progressive methodology spanning five verification levels: unit property testing, integration property testing, formal Lean 4 proofs, contract validation, and fault injection analysis.

**Black Team (2 agents)** -- Theoretical Threat Modeling. Operates under maximum isolation constraints. Produces abstract threat models analyzing worst-case adversarial optimization scenarios. The Black team never produces executable content; all output passes through an L1-L4 abstraction filter enforced by the dedicated Abstraction Enforcer agent.

### 7.2 Safety Protocols

All security operations enforce strict safety constraints: sandbox isolation for Red and Black operations, synthetic data only (no PII, no production state), zero network access for adversarial simulations, automated ethics checks at 10-to-15-second intervals, immutable audit logging, and escalation guards that prevent scope creep from lower-risk operations into higher-risk domains.

## 11. Conclusion

Prismatic Platform represents a departure from the conventional model of intelligence and security tooling as a collection of loosely integrated point solutions. By unifying OSINT collection, attack surface management, due diligence automation, and AI monitoring within a single epistemically rigorous runtime -- governed by formally verified reasoning, protected by adversarial-defensive security synthesis, and continuously improved through autonomous self-evolution -- the platform provides an intelligence substrate that grows more capable, more reliable, and more comprehensive with every generation.

The combination of Elixir/OTP's fault-tolerant concurrency model, the AIAD agent standard's composable autonomy, NABLA Infinity's epistemic guarantees, and the NO MERCY, NO DOUBTS doctrine's uncompromising quality enforcement creates a system where confidence in outputs is not assumed but continuously verified, where security is not a feature but an emergent property of adversarial testing, and where evolution is not a roadmap item but an automated process that runs every session.

The platform is production-deployed, continuously evolving, and open for exploration through the documentation sections linked above.
