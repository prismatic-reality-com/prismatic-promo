## Overview

**Performance tracking** is the discipline of systematically measuring, recording, analyzing, and acting on performance data generated by software systems in development, staging, and production environments. It encompasses everything from low-level function execution timing to high-level user experience metrics, providing the quantitative foundation for reliability engineering, capacity planning, and service-level objective (SLO) compliance.

In the [Prismatic Platform](@/glossary/application.md), performance tracking is not optional -- it is a P0 absolute requirement. Every page must load under 250ms, every server-side render must complete under 100ms, and every LiveView event handler must respond within 50ms. These are not aspirational targets; they are enforced through [quality gates](@/glossary/quality-gates.md), pre-commit hooks, and [CI/CD](@/glossary/ci-cd.md) pipeline checks that block deployment of any code violating these thresholds.

This entry covers the theory, methodologies, tools, and implementation patterns that make rigorous performance tracking possible in Elixir/Phoenix applications and beyond.

## Definition and Importance

Performance tracking is the continuous process of collecting, aggregating, and analyzing quantitative measurements of system behavior -- [latency](@/glossary/latency.md), [throughput](@/glossary/throughput.md), error rates, resource utilization -- to ensure that applications meet defined service-level objectives and to detect degradation before it impacts users.

The importance of performance tracking in production systems cannot be overstated:

- **User experience**: Research consistently shows that every 100ms of additional latency reduces conversion rates by 1-7%. Users abandon pages that take more than 3 seconds to load.
- **Revenue impact**: Amazon famously calculated that every 100ms of latency cost them 1% in sales. Google found that an extra 500ms in search results reduced traffic by 20%.
- **Reliability**: Performance degradation is often the first symptom of deeper issues -- memory leaks, database contention, network saturation, or cascading failures.
- **Capacity planning**: Historical performance data enables accurate forecasting of infrastructure needs, preventing both over-provisioning (wasted cost) and under-provisioning (outages).
- **SLO compliance**: Modern platform engineering requires quantifiable service-level objectives backed by real measurement data, not assumptions.

## Historical Context

Performance tracking has evolved dramatically from its origins in mainframe-era system monitoring.

**1960s-1970s -- System Monitors**: Early mainframe operating systems provided rudimentary CPU and memory utilization metrics. Operators manually inspected printouts and console displays.

**1980s -- Network Monitoring**: SNMP (Simple Network Management Protocol) enabled automated polling of network device metrics. Tools like MRTG visualized bandwidth utilization over time.

**1990s -- Application Performance Management**: The rise of web applications drove demand for application-level monitoring. Companies like Wily Technology (later acquired by CA) pioneered agent-based APM that instrumented Java bytecode to track transaction response times.

**2000s -- Distributed Tracing Origins**: Google's Dapper paper (2010) and its open-source descendants (Zipkin, Jaeger) introduced [distributed tracing](@/glossary/distributed-tracing.md) -- the ability to follow a request across multiple services and correlate latency contributions.

**2010s -- Observability Movement**: The term "[observability](@/glossary/observability.md)" (borrowed from control theory) gained traction, expanding beyond [metrics](@/glossary/metrics.md) to encompass logs, traces, and events as complementary signals. The RED and USE methods provided structured frameworks for what to measure.

**2020s -- OpenTelemetry and Convergence**: OpenTelemetry emerged as the vendor-neutral standard for instrumentation, unifying metrics, traces, and logs under a single API. Elixir's `:telemetry` library brought the same principles to the BEAM ecosystem with minimal overhead.

## Core Concepts: Key Metrics

### Latency Percentiles

Latency -- the time between a request being sent and a response being received -- is the most user-visible performance metric. Raw averages are misleading because they hide tail latency. Percentile measurements provide a complete picture:

- **P50 (median)**: Half of requests are faster than this value. Represents the "typical" user experience.
- **P95**: 95% of requests are faster. Captures the experience of users on slower connections or hitting more complex code paths.
- **P99**: 99% of requests are faster. Reveals tail latency caused by garbage collection pauses, cold caches, or database lock contention.
- **P99.9**: Critical for high-traffic systems where even 0.1% of slow requests affects thousands of users.

The Prismatic Platform enforces specific latency budgets:

| Component | P95 Limit | Enforcement |
|-----------|-----------|-------------|
| Total page load | 250ms | Merge blocked |
| Server-side render | 100ms | Merge blocked |
| LiveView mount | 150ms | Merge blocked |
| LiveView handle_event | 50ms | Merge blocked |
| Health check | 10ms | Merge blocked |

### Throughput

[Throughput](@/glossary/throughput.md) measures the rate at which a system processes requests, typically expressed as requests per second (RPS) or transactions per second (TPS). Throughput and latency are related but distinct: a system can have low latency but also low throughput (processing few requests, each quickly) or high throughput with high latency (processing many requests, each slowly due to queuing).

### Error Rates

The percentage of requests that result in errors (HTTP 5xx, exceptions, timeouts). Error rates should be tracked both globally and per-endpoint. A spike in error rate often precedes a latency spike as retry logic kicks in.

### Saturation

How "full" a resource is -- CPU utilization, memory consumption, disk I/O queue depth, connection pool usage, message queue backlog. Saturation metrics are leading indicators: they predict future problems before they manifest as latency or errors.

## RED and USE Methodologies

### RED Method (Request-Scoped)

Developed by Tom Wilkie at Grafana Labs, RED focuses on request-driven services:

- **Rate**: Requests per second being handled
- **Errors**: Number of failed requests per second
- **Duration**: Distribution of request latency (histograms, not averages)

RED is ideal for microservices and web applications where the unit of work is a discrete request. In Phoenix applications, RED metrics map naturally to endpoint-level [telemetry](@/glossary/telemetry.md) events.

### USE Method (Resource-Scoped)

Developed by Brendan Gregg, USE focuses on infrastructure resources:

- **Utilization**: Percentage of time the resource is busy (or percentage of capacity used)
- **Saturation**: Degree to which the resource has extra work it cannot service (queue length)
- **Errors**: Count of error events for the resource

USE is applied to every physical and logical resource: CPUs, memory, disks, network interfaces, BEAM schedulers, ETS tables, and database connection pools. USE and RED are complementary -- apply RED to services and USE to the resources those services consume.

## Technical Deep Dive: Telemetry in Elixir/Phoenix

The Elixir ecosystem provides first-class performance tracking through the `:telemetry` library -- a lightweight, dynamic dispatching library for metrics and instrumentation built into the BEAM ecosystem.

### Architecture

The `:telemetry` library follows a publish-subscribe pattern:

1. **Instrumentation points** emit events with measurements and metadata using `:telemetry.execute/3`
2. **Handlers** attach to event names and process measurements (aggregate, forward to backends, trigger alerts)
3. **Reporters** send aggregated metrics to external systems (Prometheus, StatsD, DataDog)

Phoenix, Ecto, and other libraries ship with built-in telemetry events, providing comprehensive [observability](@/glossary/observability.md) out of the box.

### Core Events in Phoenix

Phoenix emits telemetry events at every critical point in the request lifecycle:

- `[:phoenix, :endpoint, :start]` -- HTTP request received
- `[:phoenix, :endpoint, :stop]` -- HTTP response sent (includes duration)
- `[:phoenix, :router_dispatch, :start]` -- Route matched
- `[:phoenix, :live_view, :mount, :start | :stop]` -- LiveView mount lifecycle
- `[:phoenix, :live_view, :handle_event, :start | :stop]` -- LiveView event handling
- `[:phoenix, :channel_joined]` -- WebSocket channel joined

### Ecto Database Events

- `[:prismatic, :repo, :query]` -- Database query executed (includes query time, decode time, queue time)

These events provide the raw data needed to enforce the Prismatic Platform's performance standards.

## Prismatic Platform Implementation

### Performance Policy Enforcement

The Prismatic Platform enforces performance standards through multiple layers:

```elixir
# Performance check mix task (simplified)
defmodule Mix.Tasks.Performance.Check do
  @moduledoc "Validates page load performance against P0 standards."
  use Mix.Task

  @page_load_limit_ms 250
  @server_render_limit_ms 100
  @live_view_mount_limit_ms 150
  @handle_event_limit_ms 50

  @impl Mix.Task
  def run(_args) do
    results = run_benchmarks()

    violations =
      Enum.filter(results, fn result ->
        result.p95_ms > limit_for(result.category)
      end)

    case violations do
      [] ->
        Mix.shell().info("All performance checks passed.")

      violations ->
        for v <- violations do
          Mix.shell().error(
            "VIOLATION: #{v.name} P95=#{v.p95_ms}ms exceeds #{limit_for(v.category)}ms limit"
          )
        end

        Mix.raise("Performance check failed. #{length(violations)} violation(s) detected.")
    end
  end

  defp limit_for(:page_load), do: @page_load_limit_ms
  defp limit_for(:server_render), do: @server_render_limit_ms
  defp limit_for(:live_view_mount), do: @live_view_mount_limit_ms
  defp limit_for(:handle_event), do: @handle_event_limit_ms
end
```

### Telemetry Metrics Configuration

```elixir
defmodule PrismaticWeb.Telemetry do
  use Supervisor
  import Telemetry.Metrics

  def start_link(arg) do
    Supervisor.start_link(__MODULE__, arg, name: __MODULE__)
  end

  @impl Supervisor
  def init(_arg) do
    children = [
      {:telemetry_poller, measurements: periodic_measurements(), period: 10_000},
      {TelemetryMetricsPrometheus, metrics: metrics()}
    ]

    Supervisor.init(children, strategy: :one_for_one)
  end

  defp metrics do
    [
      # Phoenix endpoint latency distribution
      distribution("phoenix.endpoint.stop.duration",
        unit: {:native, :millisecond},
        reporter_options: [buckets: [10, 25, 50, 100, 150, 250, 500, 1000]],
        tags: [:method, :route]
      ),

      # LiveView mount latency
      distribution("phoenix.live_view.mount.stop.duration",
        unit: {:native, :millisecond},
        tags: [:view]
      ),

      # LiveView event handling latency
      distribution("phoenix.live_view.handle_event.stop.duration",
        unit: {:native, :millisecond},
        tags: [:view, :event]
      ),

      # Database query latency
      distribution("prismatic.repo.query.total_time",
        unit: {:native, :millisecond},
        tags: [:source]
      ),

      # VM metrics
      last_value("vm.memory.total", unit: :byte),
      last_value("vm.total_run_queue_lengths.total"),
      last_value("vm.total_run_queue_lengths.cpu"),
      last_value("vm.total_run_queue_lengths.io"),
      summary("vm.system_counts.process_count")
    ]
  end

  defp periodic_measurements do
    [
      {PrismaticWeb.Telemetry, :dispatch_ets_stats, []},
      {PrismaticWeb.Telemetry, :dispatch_pool_stats, []}
    ]
  end

  def dispatch_ets_stats do
    for table <- :ets.all(), info = :ets.info(table), is_list(info) do
      :telemetry.execute(
        [:prismatic, :ets, :table],
        %{size: info[:size], memory: info[:memory]},
        %{table: info[:name]}
      )
    end
  end

  def dispatch_pool_stats do
    case DBConnection.get_connection_metrics(Prismatic.Repo) do
      {:ok, metrics} ->
        :telemetry.execute(
          [:prismatic, :db_pool],
          %{
            idle: metrics.idle,
            busy: metrics.busy,
            checkout_queue_length: metrics.checkout_queue_length
          },
          %{}
        )

      _ ->
        :ok
    end
  end
end
```

### Custom Telemetry Event Emission

```elixir
defmodule PrismaticWeb.PerformanceInstrumentation do
  @moduledoc """
  Custom performance instrumentation for critical platform operations.
  Emits telemetry events with measurements and metadata for tracking
  against P0 performance standards.
  """

  def measure_operation(event_name, metadata, fun) when is_function(fun, 0) do
    start_time = System.monotonic_time()

    try do
      result = fun.()

      :telemetry.execute(
        [:prismatic, :performance | event_name],
        %{duration: System.monotonic_time() - start_time},
        Map.put(metadata, :status, :ok)
      )

      {:ok, result}
    rescue
      error ->
        :telemetry.execute(
          [:prismatic, :performance | event_name],
          %{duration: System.monotonic_time() - start_time},
          Map.merge(metadata, %{status: :error, error: Exception.message(error)})
        )

        {:error, error}
    end
  end
end
```

## APM Tools and Integration

### OpenTelemetry

OpenTelemetry is the vendor-neutral observability framework that the industry has converged on. The Elixir ecosystem provides full OpenTelemetry support:

- `opentelemetry_api` -- API for creating spans and recording metrics
- `opentelemetry_exporter` -- OTLP exporter for sending data to collectors
- `opentelemetry_phoenix` -- Automatic instrumentation for Phoenix endpoints
- `opentelemetry_ecto` -- Automatic instrumentation for Ecto queries
- `opentelemetry_liveview` -- LiveView mount and event instrumentation

### Commercial APM

| Tool | Strengths | Integration |
|------|-----------|-------------|
| **DataDog** | Full-stack observability, APM + infrastructure + logs | `datadog-agent` + StatsD telemetry reporter |
| **New Relic** | Transaction tracing, error analytics, browser monitoring | `new_relic_agent` hex package |
| **Grafana Cloud** | Open-source stack (Prometheus + Loki + Tempo), cost-effective | Prometheus telemetry reporter |
| **Honeycomb** | High-cardinality event analysis, BubbleUp feature | OpenTelemetry OTLP exporter |

### Choosing an Approach

For the Prismatic Platform, the preferred stack is `:telemetry` (instrumentation) combined with Prometheus (metrics storage) and Grafana (visualization). This provides full control over data retention, avoids vendor lock-in, and integrates natively with the Elixir ecosystem.

## Performance Budgets and Regression Detection

A **performance budget** is a quantitative limit on a performance metric that must not be exceeded. Budgets transform performance from a subjective concern into an objective, enforceable constraint.

### Budget Categories

- **Time budgets**: Maximum allowed latency for specific operations (e.g., 250ms page load)
- **Size budgets**: Maximum payload sizes for JavaScript bundles, CSS, images, and API responses
- **Resource budgets**: Maximum CPU time, memory allocation, or database query count per request
- **Count budgets**: Maximum number of HTTP requests, database queries, or external API calls per page load

### Regression Detection

Performance regressions are detected through:

1. **Baseline establishment**: Benchee runs capture baseline metrics for critical paths
2. **Threshold comparison**: New measurements are compared against baselines with defined tolerance (typically 10-15%)
3. **Statistical significance**: Random variation is distinguished from genuine regression using statistical tests
4. **Automated alerting**: Violations trigger notifications through [monitoring](@/glossary/monitoring.md) pipelines

The Prismatic Platform's pre-commit hooks (Phase 8) and CI/CD gates enforce performance budgets automatically. Code that introduces a measurable regression is blocked from merging.

## Real User Monitoring vs Synthetic Monitoring

### Real User Monitoring (RUM)

RUM collects performance data from actual user sessions in production:

- **Advantages**: Reflects real-world conditions (diverse devices, networks, geographic locations), captures long-tail performance issues, provides user-centric metrics (LCP, FID, CLS)
- **Disadvantages**: Requires production traffic, privacy considerations (data collection consent), noisy data requiring statistical aggregation
- **Implementation**: Browser Performance API, Navigation Timing API, or commercial RUM tools (DataDog RUM, Sentry Performance)

### Synthetic Monitoring

Synthetic monitoring executes predefined transactions from controlled environments at regular intervals:

- **Advantages**: Consistent baselines, early detection (works before production traffic), controlled conditions, no user privacy concerns
- **Disadvantages**: Does not capture real-world variability, limited to predefined scenarios, may miss issues only triggered by specific user behaviors
- **Implementation**: Lighthouse CI, WebPageTest, Playwright-based synthetic tests, or custom Benchee suites

### Combined Strategy

Production systems should use both approaches. Synthetic monitoring catches regressions in CI/CD before deployment. RUM validates that real users experience acceptable performance after deployment. The Prismatic Platform uses Benchee-based synthetic tests in CI and `:telemetry`-based production monitoring for comprehensive coverage.

## Performance Tracking in CI/CD Pipelines

Integrating performance tracking into [CI/CD](@/glossary/ci-cd.md) pipelines transforms performance from a reactive concern into a proactive engineering discipline.

### Pipeline Stages

1. **Build stage**: Measure compilation time and asset bundle sizes. Flag regressions in bundle size exceeding thresholds.
2. **Test stage**: Run Benchee performance tests alongside functional tests. Compare results against stored baselines.
3. **Performance gate**: Dedicated pipeline stage that blocks deployment if any performance budget is exceeded. In the Prismatic Platform, this is `mix performance.check` with exit code 1 on violation.
4. **Staging validation**: Deploy to staging environment and run synthetic transaction tests under realistic load.
5. **Canary deployment**: Route a small percentage of production traffic to the new version and compare RUM metrics against the stable version.
6. **Production monitoring**: Continuous `:telemetry` collection with automated alerting at P95 thresholds.

## Best Practices

1. **Measure everything, alert selectively**: Instrument comprehensively but only page operations teams for actionable conditions. Alert fatigue is the enemy of effective monitoring.
2. **Use percentiles, not averages**: Averages hide tail latency. Always track P50, P95, P99, and P99.9. Set SLOs on P95 or P99, not on averages.
3. **Set budgets before writing code**: Define performance requirements as part of design, not as an afterthought. The Prismatic Platform's 250ms page load standard exists before any feature work begins.
4. **Track trends, not just thresholds**: A metric that is within budget but trending upward requires investigation before it becomes a violation.
5. **Correlate metrics across layers**: When latency increases, correlate with database query times, external API calls, BEAM scheduler utilization, and garbage collection pauses to identify root cause.
6. **Automate regression detection**: Manual performance reviews do not scale. Integrate Benchee baselines and `mix performance.check` into CI/CD pipelines.
7. **Profile in production**: Development environments do not reproduce production load characteristics. Use `:telemetry` and `:recon` for production profiling with minimal overhead.
8. **Separate read and write paths**: Read-heavy and write-heavy operations have different performance characteristics. Track them independently.

## Anti-Patterns

- **Average-only monitoring**: Reporting only average latency hides the experience of users hitting the long tail. A system with 50ms average and 5-second P99 has a serious problem that averages conceal.
- **Dashboard-only observability**: Dashboards are for humans looking at screens. Automated alerting and CI/CD gates are for systems that enforce standards 24/7. Without automation, performance standards are aspirations, not requirements.
- **Sampling without understanding**: Aggressive sampling (e.g., tracking only 1% of requests) can miss intermittent performance issues. Understand the statistical implications of your sampling rate.
- **Micro-benchmarking in isolation**: Benchmarking individual functions without realistic load, concurrency, and data volume produces misleading results. Micro-benchmarks should complement, not replace, system-level performance tests.
- **Ignoring warm-up effects**: BEAM VM warm-up (JIT compilation in OTP 26+, ETS table population, connection pool initialization) means initial requests are slower than steady-state. Account for warm-up in benchmarks and do not include cold-start measurements in baseline comparisons.
- **Over-instrumenting hot paths**: Adding telemetry to extremely high-frequency code paths (per-message processing in GenStage pipelines) can itself become a performance bottleneck. Use sampling or aggregation for hot paths.
- **Chasing vanity metrics**: Tracking hundreds of metrics without clear ownership or action plans creates noise. Every tracked metric should have an owner, a threshold, and a documented response procedure.

## Related Technologies

- **Prometheus**: Time-series database optimized for metrics storage, with a powerful query language (PromQL) and native Elixir integration through `telemetry_metrics_prometheus`
- **Grafana**: Visualization platform supporting Prometheus, Loki, Tempo, and dozens of other data sources for dashboards and alerting
- **Benchee**: Elixir benchmarking library providing statistically rigorous comparisons with memory measurement, reduction counting, and multiple output formats
- **:recon**: Erlang/OTP production debugging tool for process inspection, memory analysis, and scheduler profiling without service interruption
- **:observer**: Built-in BEAM tool providing real-time visualization of process trees, ETS tables, memory usage, and scheduler utilization
- **Flame Graphs**: Visualization technique for identifying CPU-intensive code paths, supported by `:eflame` and `:eflambe` in the BEAM ecosystem

## Future Directions

Performance tracking continues to evolve alongside the systems it monitors:

- **AI-driven anomaly detection**: [Machine learning](@/glossary/machine-learning.md) models that learn normal performance patterns and automatically detect anomalies without manually configured thresholds
- **Predictive scaling**: Using historical performance data and traffic patterns to proactively scale infrastructure before demand spikes
- **Continuous profiling**: Always-on, low-overhead production profiling (tools like Pyroscope, Parca) that captures CPU and memory profiles continuously, not just during incidents
- **eBPF-based observability**: Linux kernel-level instrumentation providing unprecedented visibility into system behavior without application code changes
- **SLO-driven development**: Shifting from performance as a testing concern to performance as a product requirement, with error budgets governing deployment velocity
- **Edge performance tracking**: As computation moves to CDN edges and serverless functions, performance tracking must follow, measuring cold start times, edge cache hit rates, and geographic latency distribution
- **WebAssembly performance**: WASM-based computation in browsers and on servers introduces new performance characteristics requiring specialized tracking
