1. Platform Overview / Co je platforma

This section addresses foundational questions: what the platform is, what problem it solves, who it serves, what it is built on, and what "Generation 19" means.

1.1 What is the Prismatic Platform?

TL;DR · A single-runtime, Elixir/OTP intelligence-and-development infrastructure with 552 AIAD agents, 92 umbrella apps, 121+ OSINT sources, and a 19-pillar enforcement doctrine.

The Prismatic Platform is an AI-orchestrated intelligence, security, and development infrastructure implemented as an Elixir umbrella project. It comprises 92 OTP applications running on a single BEAM virtual machine, coordinated through supervision trees, PubSub event buses, and a pluggable storage adapter layer. The platform hosts 552 autonomous AI agents operating across 14 domains — from open-source intelligence gathering and external attack surface management to formal verification with Lean 4 theorem proofs.

At its core, the platform unifies capabilities that are typically fragmented across dozens of separate tools: OSINT data collection from 121+ sources, due diligence investigation workflows, security rating computation comparable to products like BitSight and SecurityScorecard, AI agent orchestration with epistemic quality controls, and a self-evolving quality infrastructure under the SEADF framework that has progressed through 19 generations of autonomous improvement. The entire system achieves microsecond inter-service latency without the operational complexity of distributed microservices, because all applications share the same Erlang runtime.

Deep dive · See /architecture/umbrella-apps/ for the application taxonomy, /registry/agents/ for the agent catalog, and /capabilities/aiad-standard/ for the AIAD framework specification.

1.2 What problem does the Prismatic Platform solve?

TL;DR · Consolidates dozens of fragmented intelligence, security, compliance, and development tools into one fault-tolerant, in-process runtime where data flows by direct function call rather than network API.

Intelligence, security, and compliance operations typically require teams to integrate dozens of specialised tools — threat intelligence feeds, OSINT databases, compliance assessment frameworks, security scanners, case management systems, and reporting platforms — each with its own data model, authentication scheme, and operational overhead. The Prismatic Platform consolidates these capabilities into a single, fault-tolerant runtime where data flows between subsystems through direct function calls and in-process message passing rather than network APIs.

This consolidation eliminates several categories of operational friction. Data enrichment that would require multiple API calls across separate services happens through parallel in-process queries. Security ratings that depend on asset discovery, vulnerability assessment, and compliance mapping are computed within a single supervision tree. Intelligence workflows that combine Czech registry data, global threat feeds, and sanctions screening share a unified entity model rather than requiring ETL pipelines between disconnected systems. The same runtime that performs OSINT enrichment also persists evidence into the event-sourced audit log and renders the LiveView dashboard the analyst is looking at — without crossing a network boundary.

The second class of problem the platform addresses is epistemic discipline. Most security and intelligence platforms produce findings with implicit confidence; Prismatic enforces explicit, traceable belief formation through the NABLA Infinity framework, the Trinity Gate verification barrier, and the QEVE quantified epistemic verification engine, so every conclusion can be audited back to its source signals.

1.4 What programming languages and frameworks does the platform use?

TL;DR · Elixir on the BEAM, Phoenix for web, Ecto/PostgreSQL plus Meilisearch/KuzuDB/Redis/ETS for storage, Lean 4 for proofs, Claude+Ollama for AI, Tailwind/Flowbite for UI.

The primary implementation language is Elixir, running on the BEAM (Erlang Virtual Machine) with OTP (Open Telecom Platform) for fault tolerance and concurrency. Web interfaces are built with Phoenix Framework and LiveView for real-time server-rendered dashboards. The data layer uses PostgreSQL via Ecto as the primary relational store, ETS (Erlang Term Storage) for high-speed in-memory caching, Meilisearch for full-text search, KuzuDB for graph queries, and Redis for distributed caching and rate limiting. Formal verification uses Lean 4 for theorem proving. AI capabilities integrate Claude (Anthropic) for complex reasoning and local Ollama models (qwen3-coder, deepseek-coder, gpt-oss:20b) for low-latency inference. The front-end styling uses TailwindCSS with Flowbite components exclusively — custom CSS and inline styles are forbidden by the FLLM doctrine pillar.

1.5 What does "Generation 19" mean?

TL;DR · A counter for measurable autonomous improvement cycles applied across the codebase — not a semantic version. Generation 19 reflects ongoing platform evolution under SEADF.

The platform tracks its evolutionary state using a generation counter. Each generation represents a measurable improvement cycle driven by autonomous evolution protocols coordinated by the SEADF framework and triggered through commands like /evolve, /auto, and /mycelialize. These protocols scan for quality improvements, detect code patterns that can be optimized, eliminate technical debt, and validate that the platform's fitness score (a composite metric covering quality, performance, and architectural health) improves or at least does not regress.

The platform has progressed from Generation 1 through Generation 19, achieving fitness scores in the 0.998–0.999 range — near the theoretical maximum. This is not a semantic version in the traditional sense; it reflects the cumulative effect of thousands of autonomous improvement cycles applied across the platform's 2.8 million lines of code. The current generation is reported by mix health.score and persisted in .claude/quality-dna/current-state.json for trend analysis.

2. Architecture and Design / Architektura a návrh

These questions cover the technical decisions underlying the platform's structure, runtime characteristics, and data architecture.

2.1 Why was Elixir/OTP chosen over other technology stacks?

TL;DR · Three requirements disqualify most runtimes: preemptive lightweight processes, per-process garbage collection with crash isolation, and hot code loading. BEAM/OTP is the only mature runtime that satisfies all three.

The choice is driven by three requirements that disqualify most runtime environments:

  1. Preemptive scheduling. The BEAM scheduler provides preemptive scheduling across lightweight processes with sub-millisecond context switching, which is essential when 552 AI agents, LiveView dashboard connections, and background crawl jobs share the same runtime. Cooperatively-scheduled runtimes (Node.js, Python asyncio) cannot guarantee fair scheduling under load; thread-based runtimes (JVM, .NET) carry orders-of-magnitude higher per-task memory.
  2. Crash isolation. Each Erlang process has its own heap and garbage-collects independently, meaning a crash in one process does not corrupt another's memory — OTP supervisors automatically restart failed processes according to configurable strategies, making the system self-healing at the process level.
  3. Hot code loading. The BEAM supports hot code loading, enabling module replacement in a running system without dropping connections — directly relevant to the zero-downtime operations capability.

The platform also enforces a meta-rule to maintain idiomatic Elixir: "If the same solution could be written identically in Node.js, it is WRONG." This is documented in the platform's development module and enforced by Credo custom checks.

2.2 Why an umbrella project rather than microservices?

TL;DR · Microservice-like modularity (independent compilation, isolated tests, explicit deps) without microservice operational overhead — no service discovery, no network serialization, no container fleet, microsecond inter-app latency.

The umbrella structure provides microservice-like modularity — independent compilation, isolated testing, explicit dependency declarations enforced at compile time — without microservice operational overhead. There is no service discovery, no network serialization between components, no distributed tracing requirement, and no container orchestration complexity. All 92 applications share a single BEAM node, communicating through direct function calls and message passing with microsecond latency.

A failure in the Perimeter application's supervision tree does not propagate to the Web application's supervision tree because the top-level supervisor uses the :one_for_one restart strategy. This delivers fault isolation equivalent to separate services while maintaining the deployment simplicity of a monolith.

The trade-off is bounded: independent horizontal scaling per microservice is replaced by per-process scaling within the BEAM, and language polyglot is sacrificed (everything must run on the BEAM). For this platform's workload — high agent concurrency, shared in-memory state, frequent inter-app calls — the umbrella choice is dominant by an order of magnitude in latency and operational cost.

2.3 What is the 3NL (Three Nested Levels) architectural framework?

TL;DR · Strategic / Tactical / Operational layering enforced as a coupling rule: code at one level only calls into appropriate abstractions, never reaches into a deeper level's internals.

3NL is the architectural abstraction framework that organizes all platform components across three levels:

  • Level 1 (Strategic) encompasses public APIs, facade modules, and external interfaces — the surface that consumers interact with.
  • Level 2 (Tactical) covers inter-application coordination, pipeline orchestration, and agent messaging — the connective tissue between domains.
  • Level 3 (Operational) contains OTP process internals, ETS operations, and BEAM-level optimizations — the implementation details that consumers should never depend on.

The framework ensures that code at each level interacts only with appropriate abstractions. A LiveView controller at Level 1 calls a facade function at Level 1; it never reaches into a GenServer's internal state at Level 3. This is the first of the platform's 19 enforcement pillars, formalised as the "3NL" pillar in the doctrine catalog.

2.4 What is the AIAD standard?

TL;DR · AIAD (AI-Agent Interface Definition) is the YAML-based machine-readable specification governing every agent, command, pipeline, policy, and adapter on the platform — 552 agents, 228 commands, all introspectable.

AIAD is the platform's specification format for defining agents, commands, pipelines, policies, and adapters. Every agent is defined in a YAML file under .aiad/agents/ with structured metadata including its name, domain classification, authority level (L1 through L5), available tools and capabilities, behavioural rules, input/output contracts, and compliance requirements with the NO MERCY / NO DOUBTS doctrine.

The standard enables machine-readable agent definitions that the platform's runtime can introspect, validate, and enforce. There are currently 552 AIAD-defined agents and 228 AIAD-defined commands across the platform. The AIAD auto-indexer (./.aiad/bin/aiad index) maintains a registry that keeps all agent and command metadata synchronized; the resulting catalog is exposed both at /registry/agents/ and /registry/commands/, and is queryable via the agent registry API.

The AIAD standard is vendor-neutral and polyglot — it does not assume a particular LLM vendor or a particular runtime. The current implementation runs on Elixir/BEAM, but the spec format would survive a re-implementation in another language.

The storage layer implements a behaviour-based adapter pattern through the PrismaticStorage.Adapter behaviour. All storage operations — store/3, fetch/2, delete/2, list/2 — route through this uniform interface regardless of the underlying backend. The platform currently implements five adapters:

2.6 How does supervision work in practice?

TL;DR · OTP supervision trees with :one_for_one strategies isolate failures; every GenServer has a defined restart policy; supervisor crash propagates to the application boundary, never further.

Each Prismatic umbrella application has its own supervision tree. The top-level Application module starts one or more supervisors, which in turn supervise GenServers, DynamicSupervisors, Tasks, and Registries. The most common restart strategies in use:

  • :one_for_one — only the failing child restarts. Used for siblings whose failures are independent.
  • :one_for_all — every sibling restarts when one fails. Used when children share state that becomes inconsistent on partial failure.
  • :rest_for_one — restart the failing child and every child started after it. Used for ordered initialization chains.

The platform standardizes on :one_for_one at the application top level so that a failure in one app's tree never propagates to another app. Within a tree, more aggressive strategies are used where consistency is paramount. For full background see Academy: OTP Fundamentals and Lab: Architecture Validation.

2.7 What is Phoenix PubSub used for?

TL;DR · A built-in distributed event bus connecting agents, LiveView processes, and the audit pipeline; same broadcast API works in single-node and clustered deployments.

Phoenix PubSub is the platform's in-process and inter-node event broadcast mechanism. Agents emit telemetry and domain events on named topics; LiveView processes subscribe to the topics they need to render in real time; the audit pipeline subscribes to all state-changing topics for event sourcing. The platform uses PubSub topics that combine a domain prefix and an entity identifier — for example, perimeter:scan:#{scan_id} — so subscribers can fan out by entity granularity without spamming unrelated processes.

PubSub also forms the substrate for /mycelialize cross-domain pattern propagation: when a pattern emerges in one domain, the relevant orchestrator broadcasts on a mycelium:emergence:#{pattern_id} topic, and other domains can subscribe to attempt local application.

2.8 How are PostgreSQL and KuzuDB combined?

TL;DR · PostgreSQL holds canonical entity records and transactional state; KuzuDB holds the relationship graph computed from those records. Updates flow Postgres → KuzuDB via change capture.

The platform combines PostgreSQL and KuzuDB in a hybrid relational-graph model. Postgres holds the canonical entity records — companies, persons, domains, emails, IPs — with their attributes, history, and transactional consistency. KuzuDB holds the relationship graph: ownership chains, director networks, address co-occurrence, infrastructure adjacency. Updates to canonical Postgres rows trigger relationship recomputation in KuzuDB through an event-sourced change-data-capture pipeline.

This split lets the platform serve two access patterns at appropriate speed: SQL aggregations and pivot tables run against Postgres, while traversal queries ("show me every Czech company sharing a director with target X within three hops") run against KuzuDB. The DD case-management workflow uses both: entity summary cards pull from Postgres, the visualization graph pulls from KuzuDB.

3.4 What is NABLA Infinity and the Trinity Gate?

TL;DR · NABLA Infinity (∇∞) is the platform's epistemic framework with seven non-negotiable axioms; the Trinity Gate is the three-layer validation barrier that every belief must pass before it can influence a decision.

NABLA Infinity is the platform's epistemic framework governing how beliefs are formed, validated, and propagated through the system. It enforces seven non-negotiable axioms:

  1. Signal Plurality — minimum two independent signals for any belief.
  2. Contradiction Evidence — both sides of conflicts must be preserved.
  3. Absence Informative — missing signals are tracked as evidence.
  4. Time Decay — mandatory timestamps on all data.
  5. Unknown Valid — "I don't know" is an acceptable and honest response.
  6. Source Independence — independent sources receive higher weight.
  7. Provenance Mandatory — all beliefs must be traceable to their origin.

The Trinity Gate is a three-layer validation barrier that every belief must pass before influencing decisions:

  • Structural Consistency — graph-theoretic validation.
  • Logical Consistency — rule-based evaluation.
  • Formal Necessity — modal logic verification with optional Lean 4 proof.

If any gate fails, the operation is halted for review. Together, NABLA + Trinity power the QEVE (Quantified Epistemic Verification Engine) that translates AI-grade scores into legally defensible conclusions — see the QEVE deep dive.

3.5 How does the AI Drift detection system work?

TL;DR · The ai_drift application monitors AI-assisted decisions for statistical drift using Kolmogorov–Smirnov and Cramér–von Mises tests; alerts fire on distribution shift; a governance registry tracks every AI-influenced decision.

The AI Drift module (application ai_drift) monitors AI-assisted decisions for statistical drift from established baselines. It uses Kolmogorov–Smirnov and Cramér–von Mises statistical tests to detect when the distribution of AI outputs has shifted significantly from the baseline distribution. When drift is detected, the system generates alerts through configurable channels (webhooks, PubSub events, dashboard notifications), logs the drift event with full provenance, and can trigger automatic baseline recomputation.

The module includes a governance decision registry for tracking which AI-influenced decisions were made and their outcomes over time. This is particularly relevant for compliance contexts (e.g., the EU AI Act and NIS2 reporting) where organizations must demonstrate that AI systems are operating within expected parameters. Sub-threshold drift detection is studied in detail at Lab: Drift Detection.

  • just test — full test suite + coverage.
  • just deploy-validate staging — deploy + post-deploy validation.

For codebase exploration, the platform provides mix git_trees (or the faster shell script ./scripts/git-trees.sh) which operates approximately 100× faster than standard find commands on the 15,000+ file repository. 4.3 How do I add a new command to the platform?

TL;DR · Same AIAD pattern: YAML under .aiad/commands/, run the indexer, command becomes available globally. 228 commands currently registered.

5.1 What does "NO MERCY, NO DOUBTS" mean in practice?

NO MERCY / NO DOUBTS is the platform's universal doctrine governing all development and operational decisions.

Violations are classified from L1 (minor deviation, warning plus immediate correction) through L4 (doubt-compromised, rejection plus supreme review).

5.5 What is the regression test protocol?

6.2 What is the NMND pillar in detail?

TL;DR · Detects TODO / FIXME / HACK / stub / placeholder patterns in lib/ code; blocks the commit with a hard error. No exemptions.

NMND (No Mercy, No Doubts) is the most-cited pillar of the doctrine and pairs with TACH and ZERO to form the production-readiness floor. It is enforced as a pre-commit grep scan over staged files: any of the patterns TODO, FIXME, HACK, XXX, pass, stub, placeholder appearing in lib/ code triggers an immediate block. Tests, scripts, and documentation are not in scope (those have their own pillars).

The pillar exists because every developer is tempted to leave "I'll come back to this later" markers — and on a 15,000-file codebase, "later" is the enemy of correctness. NMND treats half-implementations as worse than no implementation: the latter signals work-to-do, the former signals work-already-done.

6.3 What is the ZERO pillar?

TL;DR · Detects 8 BEAM-specific runtime-failure anti-patterns: bare rescue, String.to_atom/1 on user input, unsafe binary_to_term/1, unsafe map dot in HEEx, blocking GenServer.call in async handlers, and similar.

ZERO (Zero Error Runtime Operations) prevents the BEAM-specific runtime failures that the type system cannot catch:

  • bare rescue — catches everything including system exits; specific exception lists required.
  • String.to_atom/1 on unbounded input — atom table is finite and not GC'd; whitelist-based atom creation required.
  • binary_to_term/1 without :safe opt — code-injection vector.
  • Unsafe map dot notation in HEEx — raises KeyError at render time.
  • Blocking GenServer.call from a handle_info/2 — deadlock pattern.
  • Etc. — full list in policy.

Marker comments (# ZERO:RESCUE_OK - reason) above an intentionally-defensive rescue exempt that line, so the pillar can be locally suspended for justified cases like the LiveView mount hardening pattern.

Related · #q-perf · #q-seal · #q-doctrine-overview

6.4 What is the SEAL pillar?

TL;DR · Three-layer defense (pre-commit grep + Mix task + AST analysis) covering 12 OWASP Top 10 vulnerabilities: SQL injection, code injection, command injection, open redirect, path traversal, mass assignment, hardcoded secrets, log leakage, unsafe deserialization, insecure randomness, SSRF.

SEAL (Security Enforcement Absolute Lock) is the platform's security-doctrine pillar. It detects 12 OWASP Top 10 categories through a three-layer defense:

  1. Pre-commit grep — fast scan of staged files for obvious patterns (string interpolation in SQL, hardcoded API keys, Mix.shell with user input).
  2. Mix task — mix seal.validate runs deeper checks against the full codebase.
  3. AST analysis — mix credo plus custom Credo checks for context-sensitive issues.

The policy gives line-level guidance for false positives, and supports # SEAL:EXEMPT - reason markers for justified exceptions. See also the Capabilities: Compliance page and the broader security review skill.

Related · #q-zero · #q-perf · About: For Security · Capabilities: Compliance

6.5 What is the PERF pillar?

TL;DR · Detects N+1 queries, unbounded queries, string concatenation in loops, list-append in loops, blocking sync calls, inefficient empty checks. Sub-250 ms page-load fence.

PERF (Performance Engineering Runtime Fence) is the performance-discipline pillar. Static analysis at commit time detects:

  • N+1 query patterns in Ecto usage.
  • Unbounded queries missing limit/2.
  • String concatenation in loops (use interpolation or IO.iodata).
  • List append in loops (use prepend + reverse or Enum.into/2).
  • Blocking sync calls in GenServer.handle_call/3 without timeouts.
  • Inefficient empty checks (length(list) == 0 vs list == []).

Performance fences also enforce absolute limits: page load <250 ms, server render <100 ms, LiveView mount <150 ms, health check <10 ms. Misses are logged via OTEL and surfaced on the platform health dashboard.

6.6 What is the TACH pillar?

TL;DR · "Total Assurance Comprehensive Hardened" — every module needs unit tests, every pure function needs property-based tests, every cross-app boundary needs an integration test, every LiveView needs E2E.

TACH requires a four-layer test pyramid for every part of the platform. The pre-commit hook flags missing tests when source files in lib/ are added or modified without corresponding tests. The CI pipeline runs the full test suite (6,500+ files) and fails the pipeline if coverage drops below the configured floor.

Marker comments (# TACH:EXEMPT - reason) above a defmodule exempt that module, used sparingly for behaviour modules, runtime-only adapters, and modules whose coverage is delivered through their consumers' tests.

7. Color-Team Security Operations / Bezpečnostní operace barevných týmů

This section deep-dives into the color-team framework introduced in #q-color-teams.

7.1 What does the Red team actually do?

TL;DR · Adversarial simulation of epistemic attacks (truth distortion, confidence manipulation, signal poisoning, drift induction, salience hijacking) — sandboxed, synthetic data only, ethics-checked every 10–15 seconds.

The Red team consists of 4 specialized agents that simulate adversarial attacks against the platform's epistemic and decision-making layers. The five primitive attack patterns:

  1. Truth distortion — inject signals that subtly bias the NABLA Signal Plurality computation.
  2. Confidence manipulation — force confidence scores into ranges that bypass Trinity Gate thresholds.
  3. Signal poisoning — submit malformed-but-plausible source data to test downstream resilience.
  4. Drift induction — submit decision sequences calibrated to push AI Drift detection into false-negative territory.
  5. Salience hijacking — attempt to dominate the agent's attention mechanism with crafted prompts.

All Red operations run in sandboxes with synthetic data only. The Red team has no network access during operations and is monitored by the Purple team for closure — every adversarial finding becomes a defensive test case.

7.2 What does the Blue team do?

TL;DR · Defensive posture: aggregate signals, detect drift, maintain evidence synthesis pipelines, surface anomalies to the Purple team for engagement.

The Blue team consists of 4 agents responsible for the defensive side of the color-team framework. Its responsibilities:

  • Signal aggregation — collect telemetry, alerts, and OSINT findings into the intelligence synthesis pipeline.
  • Drift detection — monitor behavioral, adversarial, configuration, and anomaly drift across all monitored systems.
  • Evidence synthesis — compose multi-source evidence into NABLA-compliant belief structures.
  • Anomaly escalation — surface unusual findings to the Purple team for engagement-loop closure.

7.3 What does the Purple team do?

TL;DR · Synthesizes Red and Blue: every adversarial finding becomes a regression test; tracks closure rates, false-closure detection, and engagement metrics.

The Purple team (4 agents) operates as the orchestrator of the Red-Blue adversarial-defensive engagement loop. Its mission is to ensure that no Red finding is left without a Blue response, and no Blue defense is left without Red verification.

Concretely, the Purple team:

  • Tracks closure — every Red finding has a Blue response logged; every Blue defense has a Red verification.
  • Detects false closures — defensive responses that don't actually neutralize the attack pattern.
  • Manages regression traps — converts Red findings into permanent test cases under the TACH doctrine.
  • Reports synthesis — emits engagement metrics (closure rate, false-closure rate, regression-trap count) on a PubSub topic consumed by the executive security dashboard.

Authentication uses Bearer tokens with scope-based authorization; rate limiting per endpoint and per token is documented at /api/rate-limiting/. Errors follow a taxonomy with stable codes and HTTP semantics. Webhooks deliver real-time event notifications for security, quality, agents, and compliance topics.

A GraphQL endpoint (Absinthe + DataLoader + Phoenix subscriptions) covers typed-read use cases; the MCP endpoint exposes the same agent/command surface for Model Context Protocol consumers.

Related · #q-mcp · #q-webhooks · Academy: API Integration · API Reference

9.2 What is MCP and is it supported?

TL;DR · Model Context Protocol — Anthropic-defined standard for exposing tools/resources to LLM consumers. The platform exposes its agent catalog and command surface via MCP at /api/v1/mcp (currently feature-flagged).

The Model Context Protocol (MCP) is an open standard published by Anthropic for exposing tools, resources, and prompts to LLM-driven consumers (Claude, GPT, etc.). The Prismatic Platform exposes its 552-agent catalog and 228-command surface as MCP tools, plus a curated set of resources (glossary entries, capabilities pages, agent detail pages) for consumption by external LLM agents.

The MCP endpoint is currently feature-flagged (mcp_enabled = false in production), and is enabled selectively for partner integrations. The /mcp slash command and /mcp-service operate the local MCP server during development.

Related · #q-api · Glossary: MCP Service

9.3 How do webhooks work?

TL;DR · POST callbacks for security / quality / agent / compliance events. Configurable filters, retry on failure, signed HMAC for verification. Documented at /api/webhooks/.

Webhooks deliver event notifications to external systems via HTTP POST. Subscribers register a callback URL and a filter (event type, severity, entity scope); the platform delivers JSON-encoded events with HMAC-SHA256 signatures for verification. Failures are retried with exponential backoff up to a configurable max-attempts; permanent failures are logged and the subscription is auto-paused. Common subscription topics: perimeter.rating.changed, compliance.violation.detected, agent.status.changed, quality.score.degraded.

Related · #q-api · #q-telemetry · API: Webhooks

9.4 What is the Telemetry & OTEL pillar?

TL;DR · :telemetry library is mandatory for GenServer emit, controller logging, rescue logging, supervisor startup, external API calls. OTEL pillar enforces it.

The platform uses the :telemetry library as its observability substrate. Events are emitted from every significant action — agent dispatch, storage adapter call, DD pipeline step, LiveView mount — and consumed by metrics, alerting, and the LiveDashboard admin UI.

The OTEL doctrine pillar makes telemetry mandatory: every GenServer must emit lifecycle events, every controller/LiveView must log requests, every rescue block must log errors, every supervisor must log startup, every external API call must be instrumented. CI rejects commits that touch these surfaces without compliant instrumentation.

For consumers: telemetry events translate to Prometheus metrics, structured logs, and OpenTelemetry spans through configured handlers — the platform supports all three and ships sane defaults.

10. Deployment and Operations / Nasazení a provoz

10.1 What are the deployment requirements?

TL;DR · Single BEAM node OK for most installs; PostgreSQL required, Redis + Meilisearch recommended; Fly.io is the reference deployment target with just deploy-production.

A minimum-viable deployment runs on a single BEAM node with PostgreSQL for durable storage. For full capabilities, add Redis (distributed cache, rate limiting), Meilisearch (full-text search), and KuzuDB (graph queries). The reference deployment target is Fly.io with the just deploy-production recipe driving the three-phase production-validation doctrine (pre-deploy validate → deploy → post-deploy validate). Disk: ~5 GB for the build artifact, plus storage for OSINT cache and audit log. Memory: 2 GB minimum, 8 GB recommended for full agent fleet.

Related · #q-three-phase · Glossary: Deploy

10.2 What is the three-phase deployment doctrine?

TL;DR · Phase 1 pre-deploy validate (quality + doctrine + security), Phase 2 deploy + smoke test, Phase 3 post-deploy validate (health + functional + performance). Recovery via just production-recover.

Production deployments follow a strict three-phase sequence enforced by justfile recipes:

  1. Phase 1: Pre-deploy validate — just pre-deploy-validate runs the full quality-gate matrix, doctrine compliance check, and security scan against the local working copy. Failures block deployment.
  2. Phase 2: Deploy + smoke test — just deploy-production ships the artifact to the target and runs a fast 4-endpoint smoke test post-boot. If smoke fails, automatic rollback engages.
  3. Phase 3: Post-deploy validate — just post-deploy-validate production runs health + functional + performance checks against live endpoints. Subsuites report on LiveView page-load times (must be <250 ms), API latencies, agent registry reachability, and compliance-engine availability.

If post-deploy validation fails, just production-recover rolls back to the previous release. The full doctrine lives in .aiad/policies/production-validation-doctrine.policy.md.

Related · #q-deployment · #q-quality-gates · Capabilities: Zero-Downtime Operations

10.3 What is the recommended runtime configuration?

TL;DR · config/runtime.exs for prod env, fly.toml for Fly.io, env vars for secrets. Defaults are production-safe.

The platform follows the standard Phoenix configuration model: compile-time config in config/config.exs, environment-specific config in config/{dev,test,prod}.exs, and runtime config in config/runtime.exs (loaded at boot from environment variables for secrets). On Fly.io, fly.toml declares VM size, secrets injection, and health-check endpoints. The defaults are production-safe: SSL forced, secure cookies, SEAL pillar hardening, PERF pillar thresholds active.

For local development, copy .env.example to .env and fill in your Claude, Ollama, and database credentials. The just setup recipe handles the rest.

11.3 Doctrine vs policy vs hook vs gate — how do they relate?

TL;DR · Doctrine = principle. Policy = enforcement spec for that principle. Hook = git automation script. Gate = CI checkpoint. One doctrine pillar typically has one policy file, one or more hooks, and one or more CI gates.

Disambiguation:

  • Doctrine — a philosophical principle governing platform behavior. Examples: NMND, NWB, ZERO. Formalised as one of the 19 pillars.
  • Policy — the explicit enforcement specification for a doctrine. Lives in .aiad/policies/<acronym>-*.policy.md. Defines the checks, the markers, the violations, the bypass rules.
  • Hook — a git-automation script under .githooks/pre-commit.d/<NN>-<name> that executes one or more policy checks at commit time. Multiple hooks stack to enforce multiple doctrines.
  • Gate — a validation checkpoint in the CI pipeline (typically via mix check.doctrines or a dedicated mix <pillar>.validate) that blocks deployment on failure. Gates execute after hooks, in stricter mode (some advisory hooks become blocking gates in CI).

Concrete example for the SEAL pillar:

  • Doctrine: SEAL = "Security Enforcement Absolute Lock"
  • Policy: .aiad/policies/seal-security-enforcement.policy.md
  • Hook: .githooks/pre-commit.d/30-seal-grep
  • Gates: mix seal.validate (CI), mix check.doctrines seal (CI), mix credo custom checks (CI)
